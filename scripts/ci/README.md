# scripts/ci — задачи, которые выполняются на ПК пользователя

## Зачем это существует

Агент работает в песочнице, из которой доступны только `github.com`,
`api.github.com` и `codeload.github.com`. Ему недоступны:

* сами площадки (`pornolab.net`, `xxxclub.to`, Knaben, внешний PLAY'A API);
* логи GitHub Actions (`results-receiver.actions.githubusercontent.com`);
* артефакты GitHub Actions (`pipelines.actions.githubusercontent.com`).

Поэтому единственный способ показать агенту реальные данные — выполнить задачу
на self-hosted раннере и вернуть результат **через git**, а не через лог:

```
агент: push кода/целей  →  GitHub  →  job на раннере (ПК)  →  коммит в ci-reports  →  агент: git fetch
```

## Что здесь лежит

| Файл | Назначение |
|---|---|
| `net_probe.py` | снимает реальные HTTP-ответы площадок в отчёт |
| `targets.json` | список целей + `allowed_hosts` (единственный источник разрешённых хостов) |
| `reports-branch/` | шаблон файлов, которые живут в ветке `ci-reports` |

## Границы, которые задача не переходит

Это не пожелания, а свойства реализации — их видно в коде:

* только `GET` и `POST`; любой другой метод — отказ до первого запроса;
* хост каждой цели обязан быть в `allowed_hosts`, иначе задача падает;
* **никаких cookies**: задача не открывает `forum_cookies_*.txt`, `.env`,
  `cache.sqlite3` и вообще ничего из рабочего клона пользователя;
* в отчёт попадают только заголовки из `KEEP_HEADERS` (`content-type`,
  `server`, `location`, …) — `Set-Cookie`, `Cookie` и `Authorization`
  отбрасываются на уровне выборки и попасть в отчёт не могут;
* из тел вырезаются именованные секреты (`password=`, `bb_data=`, `token=`,
  `Bearer …`), счётчик срабатываний пишется в отчёт;
* тела обрезаются по размеру и упаковываются в gzip.

Осознанное исключение: длинные «произвольные» строки (infohash, magnet-ссылки,
имена файлов) **не** вырезаются — это ровно те данные, ради которых задача
существует.

## Как добавить новую задачу

1. Новый скрипт `scripts/ci/<task>.py` по образцу `net_probe.py`: аргументы
   `--out-dir`, запись `data/<task>.json`, код возврата `0` если отчёт записан.
2. Новый job в `.github/workflows/windows-agent-tasks.yml` (или отдельный
   workflow с `workflow_dispatch`).
3. Шаг публикации в `ci-reports` — общий для всех задач.

Задачи, которым нужны cookies или доступ к боевой базе, сюда не добавляются без
отдельного решения: они меняют модель доступа, а не просто добавляют функцию.

## Что нужно знать про запуск

`workflow_dispatch` срабатывает только если workflow уже есть в ветке `main` —
поэтому первый запуск возможен лишь после того, как PR смёржен. Ветку для
прогона можно выбрать в UI или через CLI:

```
gh workflow run windows-agent-tasks.yml --ref <ветка>
```

## Почему в workflow нет сторонних actions

Код забирается обычным `git clone`: доступ передаётся через git-конфиг в
переменных окружения (`GIT_CONFIG_*`), поэтому токен не попадает ни в
командную строку, ни в URL, ни в конфиг на диске. Так задача не зависит от
версии раннера и наличия Node — их на машине пользователя мы контролировать не
можем, а `actions/checkout@vN` от них зависит.

Первым шагом идёт `Diagnostics` — он ничего не проверяет и не падает, а печатает
в лог версии раннера, git, Python и наличие `requests`/`curl_cffi`. Это нужно
затем, что лог прогона агент прочитать не может, а вот вы — да, и первая же
неудача должна быть объяснима без переписки.
