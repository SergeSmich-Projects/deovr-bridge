# ci-reports — ветка данных, которые сняты на ПК пользователя

Эта ветка **никогда не мёржится в `main`**. Здесь нет кода — только результаты
задач, выполненных на self-hosted раннере.

Причина её существования: агент не может ни прочитать логи Actions, ни скачать
артефакты (эти хосты ему недоступны), но может читать git. Поэтому все данные
возвращаются коммитом сюда:

```
git fetch origin ci-reports
git show origin/ci-reports:data/net_probe.json
```

## Структура

```
README.md            этот файл
.gitattributes       без преобразований переводов строк
data/
  <task>.json        сводка по задаче
  <task>__<name>.*.gz  тела ответов (gzip)
```

## Что здесь запрещено

* cookies, `.env`, содержимое `cache.sqlite3`, любые токены и пароли;
* заголовки `Set-Cookie`, `Cookie`, `Authorization` — отбрасываются ещё в коде
  задачи (`scripts/ci/net_probe.py`, константа `KEEP_HEADERS`);
* именованные секреты в телах ответов — вырезаются регулярками `REDACTIONS`,
  количество срабатываний видно в отчёте в поле `redactions`.

Если в отчёте когда-нибудь окажется что-то похожее на секрет — это дефект
задачи, и его нужно чинить в `scripts/ci/`, а не подчищать вручную.

## История

Тела ответов перезаписываются каждый прогон, но не теряются: предыдущие версии
остаются в истории git этой ветки (`git log -p -- data/`). Отдельная ротация
файлов поэтому не нужна.

## Служебные поля отчёта

| Поле | Смысл |
|---|---|
| `ok` | все цели ответили без ошибок |
| `ref`, `sha`, `run_id` | из какой ветки и какого прогона сняты данные |
| `runner` | на какой машине это выполнено |
| `signals` | найденные маркеры: `antibot`, `captcha`, `cloudflare`, `login-page`, … |
| `title` | `<title>` страницы — быстрый способ понять, отдали ли то, что ожидалось |
| `history` | последние запуски по каждой цели: статус, размер, sha256 |
